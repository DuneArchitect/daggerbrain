What is Convex?

A technical overview for staff engineers — the architecture behind a reactive database that runs your TypeScript as transactions.

Built from a verified deep-research pass · 24 first-party claims confirmed (3-0) · 1 misconception refuted
02 / The one-sentence model

A cloud database that executes your API functions as transactions, inside the database

Convex collapses three layers you normally wire together yourself:

  • Database — document-relational store
  • Backend — your TypeScript functions are the API
  • Sync — results stream to clients in realtime, automatically
"The most important thing to understand: it's a database running in the cloud that runs client-defined API functions as transactions directly within the database." 1,2

Why a staff engineer should care

  • No ORM, no API layer, no cache-invalidation code, no WebSocket plumbing — they're structural, not bolted on
  • The reactivity and the ACID guarantees come from one mechanism (we'll get there)
  • The constraints it imposes (determinism, OCC) are the interesting part — and the tradeoffs

03 / Architecture

The layered runtime behind the mental model

✓ verified 3-0
CLIENT
React / Svelte / RN hook opens a WebSocket, subscribes to a query
→
FUNCTION RUNNER
Your TS runs in a V8 isolate — deterministic, sandboxed
→
COMMITTER
Validates read/write sets with OCC, writes to the log
→
SYNC ENGINE
Detects which subscriptions went stale, re-runs & pushes
Important nuance: "code inside the database" is the mental model Convex promotes. Literally, functions run in a V8 isolate function-runner while a separate committer performs OCC validation and writes. Knowing this distinction matters when you reason about latency and failure modes. 1
04 / Data model

"Document-relational"

✓ verified 3-0
  • Document — you store JSON-like nested objects
  • Relational — tables, with relations expressed as v.id("table") typed references
  • Schema is optional to start, but defining it unlocks end-to-end types
  • Indexes are explicit; queries traverse them (no query planner guessing)
System fields _id and _creationTime are added to every document automatically.
// convex/schema.ts
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

export default defineSchema({
  messages: defineTable({
    body:    v.string(),
    author:  v.id("users"),   // typed relation
    channel: v.string(),
  }).index("by_channel", ["channel"]),

  users: defineTable({ name: v.string() }),
});

// query: pure, read-only, reactive
export const list = query({
  args: { channel: v.string() },
  handler: async (ctx, args) => {
    return await ctx.db.query("messages")
      .withIndex("by_channel",
        (q) => q.eq("channel", args.channel))
      .order("desc").take(50);
  },

// action: network OK, NO ctx.db
export const summarize = action({
  args: { channel: v.string() },
  handler: async (ctx, args) => {
    const msgs = await ctx.runQuery(
      api.messages.list, args);
    const r = await fetch("https://llm…");
    await ctx.runMutation(api.messages.save, …);
  },

Serializability guarantees apply to queries & mutations only — actions are explicitly not transactions. Keep side-effecting/network code in actions; keep correctness-critical reads & writes in queries/mutations.
06 / The linchpin

Determinism is what makes everything else possible

✓ verified 3-0

A query/mutation must return the same result given the same arguments + same database read set. Convex enforces it.

How it's enforced

  • No third-party fetch in queries/mutations
  • Date.now() is frozen within a transaction
  • Math.random() is seeded/deterministic

What determinism buys you

  • Caching — identical (code, args, read set) runs once for all clients
  • Transparent retries — a conflicted mutation can just be re-run
  • Reactivity — re-running a query yields a comparable, trustworthy result
"To have these attributes the handler must be deterministic." Determinism is framed as the prerequisite for caching, reactivity, and consistency — not a side effect. 3
07 / Transactions

ACID via Optimistic Concurrency Control — no locks

✓ verified 3-0
1 · READ
Transaction records its read set (objects + observed versions)
→
2 · PROPOSE
A declarative proposal to write, based on what it read
→
3 · VALIDATE
At commit: is every read-set version still the latest?
→
4 · COMMIT / RETRY
All-or-nothing. On conflict → re-run (safe, it's deterministic)
  • Conflicts are checked at commit time, never via pessimistic locks
  • This is textbook Kung & Robinson (1981) OCC
  • You "write mutations as if they will always succeed" — atomicity is guaranteed
The honest caveat: mutations can still throw application errors, or fail with a system error after exhausting the OCC retry limit under heavy contention. "Always succeeds" is the happy path, not a hard guarantee. 4,5
08 / Isolation

True serializability — stronger than snapshot isolation

✓ verified 3-0

The claim

Convex's OCC provides true serializability: results are correct regardless of which transactions run concurrently — behaviour identical to running them one at a time.

Why that's notable

Most multi-version OCC databases give only snapshot isolation, which permits anomalies like write skew. Convex claims the strictly stronger guarantee.

Write skew (what snapshot isolation allows)

// invariant: ≥1 doctor on call
// T1 and T2 both read {A:on, B:on}
T1: if (others_on_call) A = off  // ok at snapshot
T2: if (others_on_call) B = off  // ok at snapshot
// both commit → 0 on call. Invariant broken.
// Serializable rejects one of them.
Trust boundary: this is a vendor self-assertion. Our research found no independent (e.g. Jepsen) verification — the strongest correctness claim rests on Convex's documented design intent. 4,5
09 / The "aha"

Reactivity reuses the exact same algorithm as commit-conflict detection

✓ verified 3-0

A live query subscription is, mechanically, a transaction whose read set Convex remembers. To know if its result changed, the sync engine asks the same question the committer asks:

  • Track the query's index read set + begin timestamp
  • Walk the transaction log after that timestamp
  • Does any committed write overlap the read set?
  • If yes → re-run the query, push the new result over WebSocket
"…using the exact same algorithm the committer uses for detecting serializability conflicts." One mechanism, two jobs. 1,6

Consequences

  • Every TypeScript query is realtime with zero extra config — if you use queries + the client libs 7
  • No manual cache invalidation, no pub/sub topics, no diffing
  • Reactivity is as precise as your indexes: narrow read sets = fewer needless re-runs
  • Applies to query subscriptions only — not actions, not raw HTTP
10 / Caching & consistency

Consistent snapshots + automatic caching

✓ verified 3-0

One logical timestamp per query

  • All reads in a single query run at the same logical timestamp
  • Concurrent writes do not affect that query's result mid-flight
  • You get a clean transactional snapshot — no torn reads

Automatic caching

  • Each unique (query code, params, read set) executes once across all online clients
  • Identical query + args → cached response
  • Re-execution is triggered only when the read set's data changes
Read "executes only once" as idealized: caches have finite capacity and eviction. The guarantee is about correctness of invalidation, not an absolute single execution. 3,6

export const get = query({
  args: { id: v.id("messages") },
  handler: async (ctx, { id }) => {
    const msg = await ctx.db.get(id);
    // msg: Doc<"messages"> | null
    return msg;
  },
});

// client — fully typed, reactive
const msg = useQuery(api.messages.get, {
  id, // ← must be Id<"messages">
});

14 / Tradeoffs & limits

What to weigh — and one misconception to drop

✗ includes a refuted claim

Real tradeoffs

  • OCC contention is the throughput ceiling — two transactions conflict when one writes data the other read/wrote. Hot documents serialize. 10
  • Mitigation: precise queries / narrow read sets → fewer conflicts → scale. Generalizes to any OCC DB.
  • Document & transaction limits exist (e.g. 1MB docs, bounded reads/writes per mutation) — model around them.
  • Correctness claims are vendor-asserted; no public Jepsen audit found.

✗ Refuted misconception

"Convex updates all client subscriptions simultaneously to the same global snapshot, guaranteeing cross-client consistency."

Verified 0-3 (refuted). Each client converges to fresh, consistent results — but do not assume globally-synchronized, same-instant snapshots across all clients. Design for per-client convergence, not a global clock. 7

16 / Grounded in this repo

How Daggerbrain actually uses Convex

ℹ from this codebase

One source of truth for types

Domain types are authored once in Zod, then zodToConvex generates both server validators and client form validation — the "end-to-end types" pitch, made concrete.

// schema.ts
characters: defineTable({
  owner_clerk_id: v.string(),
  campaign_id: v.optional(v.id("campaigns")),
  character: zodToConvex(CharacterSchema),
}).index("by_owner_clerk_id", ["owner_clerk_id"]);

The architecture shows up as house rules

  • No .filter() — define an index, use withIndex (queries traverse indexes)
  • No unbounded arrays in a doc — 1MB cap + every write rewrites the whole doc
  • Bounded reads — .take()/paginate, never raw .collect()
  • Split high-churn data — heartbeats/typing go in their own table to avoid write contention
  • Server is the authority — permissions & entitlements enforced in functions, never trusted from the client
Each rule is a direct consequence of the OCC + transaction-limit model from the earlier slides.
